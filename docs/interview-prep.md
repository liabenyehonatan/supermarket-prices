# הכנה לראיון פול סטאק: על בסיס הפרויקט "סלי" (Sali)

המקור לכל מה שכתוב כאן: הקוד, התיעוד וההיסטוריה של הריפו (185 קומיטים, 8-19 באוקטובר 2026). כל מספר, תקלה או החלטה שמופיעים כאן אפשר לאמת בקוד. כדאי לאמת, כי מראיין ישאל "איפה בקוד?".

---

## 0. קודם כל: מה שחייבים לדעת על הפרויקט כפי שהוא באמת

הרשימה הכללית של שאלות ראיון מניחה Node, Next.js ו-JWT. **הפרויקט שלך שונה**, ועדיף שתגידי את זה בעצמך לפני שישאלו:

| בראיון ישאלו על | בפרויקט שלך בפועל | איך לענות |
|---|---|---|
| Node, event loop | **Python 3.12 + FastAPI + asyncio** (`asyncpg`) | מושגים זהים: event loop אחד, I/O לא חוסם, `await`. תסבירי את המושג ואז "אצלי זה asyncio". |
| Next.js, SSR/SSG | **React 18 + Vite (SPA)**, מסלולים בטעינה עצלה. SEO: השרת מזריק תגיות head ו-JSON-LD לכל עמוד, ויש sitemap (`app/seo.py`) | תגידי: "בחרתי SPA כי האפליקציה אינטראקטיבית; ל-SEO פתרתי בצד שרת. Next היה נותן SSR מובנה, במחיר של עוד שרת Node." |
| React Query / server state | **אין.** state מקומי + `BasketContext` + `localStorage`, וקריאות `fetch` עם עטיפה (`api/client.ts`) | תכירי את React Query ותדעי להסביר למה לא השתמשת (ראי §6). |
| JWT, sessions, התחברות | **אין משתמשים בכלל.** בלי הרשמה, בלי cookies, הסל נשמר בדפדפן | זו החלטה מוצרית. תדעי להסביר מה הייתי מוסיפה (§10). |
| ORM / SQL | **SQLAlchemy 2.0 async + Alembic + PostgreSQL 16** | חזק. זה החלק הכי עמוק בפרויקט. |
| Docker, CI/CD | Docker Compose (7 שירותים), GitHub Actions: CI ואז deploy אוטומטי ב-SSH | חזק. |

**המסר המרכזי שלך:** "בניתי מערכת אמיתית שרצה בפרודקשן: איסוף נתונים אוטומטי פעמיים ביום, 29 רשתות, כ-2,000 חנויות, 240 אלף מוצרים, יותר מ-11 מיליון שורות מחיר. הלקחים העיקריים שלי הם ב-DB ובביצועים."

## 1. הפרויקט ב-60 שניות (לשנן)

> "סלי היא אפליקציית ווב בעברית להשוואת מחירי סופרמרקטים בישראל. החוק מחייב רשתות לפרסם קבצי מחירים, ואני אוספת אותם פעמיים ביום, טוענת ל-PostgreSQL, ומציגה: חיפוש מוצר, השוואת סל קניות בין חנויות, מבצעים שבאמת זולים מהמחיר הרגיל, חנויות קרובות וסורק ברקוד במצלמה. ה-backend ב-FastAPI אסינכרוני עם תפקיד DB לקריאה בלבד, ה-frontend ב-React ו-TypeScript, והכול רץ ב-Docker Compose על שרת אחד בישראל, כי 12 רשתות עונות רק לכתובות ישראליות. יש CI עם בדיקות ופריסה אוטומטית אחרי כל מיזוג."

### ארכיטקטורה ב-2 דקות

```
פורטלי הרשתות ─► worker ─► PostgreSQL ◄─ FastAPI (api_ro, קריאה בלבד) ◄─ nginx ◄─ React
               scrape → parse → delete                                   (Caddy = HTTPS)
```

**זרימת בקשה (חיפוש "חלב"):**
1. הדפדפן שולח `GET /api/v1/products/search?q=חלב&limit=20`.
2. Caddy מסיים HTTPS ומעביר ל-nginx. nginx בודק rate limit (20 בק'/שנייה ללקוח, burst 40) ומחפש ב-cache (GET מוחזר מהמטמון 5 דקות).
3. FastAPI מאמת פרמטרים (Pydantic/`Query`: אורך, טווחים), פותח session אסינכרוני ל-DB.
4. השאילתה: התאמת מילים עם `ILIKE` על אינדקס GIN של `pg_trgm`, דירוג לפי כמות מילים שהותאמו, אחר כך קידומת, אחר כך פופולריות (מ-materialized view `product_store_counts`).
5. התשובה חוזרת כ-JSON. ה-frontend מבקש בבקשה אחת נוספת את המחיר הכי זול לכל כרטיס (`price-summary-batch`), במקום בקשה לכל מוצר.

**זרימת נתונים (ה-worker):** פעמיים ביום (06:00 ו-18:00 שעון ישראל) לכל רשת, כתהליך נפרד עם timeout: הורדת קבצי XML ← בדיקת שלמות ← טעינה בטרנזקציה אחת יחד עם שורה ב-ledger ← מחיקת הקובץ ← רענון ה-views.

## 2. למה ה-stack הזה, ומה היו האלטרנטיבות

| בחירה | למה | אלטרנטיבה ולמה לא |
|---|---|---|
| **Python + FastAPI** | הספריות לפירוק קבצי המחירים הישראליים כתובות ב-Python. ל-FastAPI יש אסינכרוני, ולידציה אוטומטית ותיעוד | Node/Express: הייתי צריכה לכתוב מחדש את הסקרייפרים והפרסרים |
| **PostgreSQL** | נתונים רלציוניים מובהקים (רשת ← חנות ← מחיר ← מוצר), אינדקסים חלקיים, `pg_trgm` לחיפוש עברי עם שגיאות כתיב, materialized views, נעילות advisory | MongoDB: אין צורך בגמישות סכמה, וה-JOIN-ים והאגרגציות הם לב המערכת |
| **VPS אחד בישראל** | 12 רשתות חוסמות כתובות זרות (נבדק). עלות נמוכה | **Supabase + Vercel (גרסה 1 של התכנון, נפסלה):** מכסת 500MB קטנה מדי, לטנטיות בין שרת ל-DB, וסקרייפינג לא מתאים ל-serverless |
| **React + Vite** | אפליקציה אינטראקטיבית (סל, סורק, מסננים), בנייה מהירה | Next.js: SSR מובנה ל-SEO, אבל עוד שרת Node לתחזק |
| **Docker Compose** | שרת אחד, פשוט לשחזור | Kubernetes: ענק מדי לשרת אחד |
| **Caddy** | HTTPS אוטומטי (Let's Encrypt) בשורת קונפיגורציה | certbot ידני |
| **CSS בכתב יד** | שליטה ב-RTL, בלי תלות | Tailwind: אפשרי, פשוט לא נדרש |

## 3. סיפורי כשל ופתרון (הכי חשוב לראיון)

מבנה לכל סיפור: **מצב, תסמין, שורש הבעיה, תיקון, לקח.** כל אחד מהם נמצא בהיסטוריית ה-git.

### סיפור 1: שאילתה שהייתה איטית פי 3000 בגלל `IS TRUE`
- **מצב:** טעינת המחירים היומית שלקחה שעות ושמה את ה-DB (2 ליבות) על 100% CPU.
- **שורש:** בקוד כתבתי `Price.is_current.is_(True)`, ש-SQLAlchemy מתרגם ל-`is_current IS true`. PostgreSQL **לא מתאים** את זה לאינדקס חלקי שהוגדר `WHERE is_current`. כל chunk עשה Seq Scan על 11.6 מיליון שורות (3 שניות) במקום Index Scan (1.1 מילישניות).
- **תיקון:** `Price.is_current` בלי `.is_(True)`, ובדיקת רגרסיה שחוסמת את הדפוס.
- **לקח:** תמיד `EXPLAIN ANALYZE`. אינדקס חלקי עובד רק אם התנאי בשאילתה מתאים לתנאי באינדקס.

### סיפור 2: עדכון יומי של 11.5 מיליון שורות
- **תסמין:** כל בוקר ה-DB ב-200% CPU יותר מ-6 שעות והטבלה "התנפחה" (bloat).
- **שורש:** כל מחיר שלא השתנה עודכן ב-`UPDATE` רק כדי לסמן "נראה שוב". ב-PostgreSQL כל UPDATE יוצר גרסת שורה חדשה (MVCC), ולכן הרבה כתיבות ו-bloat.
- **תיקון:** מחיר שלא השתנה **לא נכתב**. קובץ Full תקין מעדכן שדה אחד לחנות (`stores.last_full_at`). ה-API מחשב "עודכן לאחרונה" לפי הגדול מבין שניהם.
- **תוצאה:** סבב מ-6+ שעות ל-20-30 דקות (לפי ה-README).
- **שיפור נפרד באותו נושא:** טעינה מרוכזת בקבוצות של 500 במקום שורה-שורה. אותם 6 קבצים: 30.7 שניות ו-81,800 שאילתות ← 3.4 שניות ו-1,126 שאילתות (מסמך ה-HLD, §8).
- **לקח:** הכתיבה היקרה ביותר היא זו שלא צריך לעשות.

### סיפור 3: חיפוש שלקח 9 שניות
- **שורש:** דירוג לפי פופולריות עשה `GROUP BY` חי על כל המחירים הנוכחיים בכל חיפוש.
- **תיקון:** `product_store_counts`, materialized view שה-worker מרענן `CONCURRENTLY` בסוף כל סבב. החיפוש רק עושה JOIN אליו.
- **לקח:** חישוב כבד שמשתנה פעמיים ביום לא שייך לבקשת משתמש.

### סיפור 4: 9 רשתות "נטענו" עם אפס קבצים ושקט מוחלט
- **תסמין:** 9 רשתות נעלמו מהאתר, בלי שגיאה בלוגים.
- **שורש:** הקבצים ירדו כ-gzip בלי סיומת `.xml`. הטוען חיפש `*.xml`, לא מצא כלום, ודיווח "הצליח, 0 קבצים".
- **תיקון:** פריסת gzip לפני הגילוי, ובהמשך גם **watchdog** שמתריע כשרשת לא נטענה חמישה ימים, ו-`/health/data` שמחזיר 503.
- **לקח:** "הצליח עם 0 תוצאות" הוא כשל. כל תהליך אוטומטי צריך ניטור לתוצאה ולא רק לשגיאה.

### סיפור 5: "מחיר ישן · עודכן לפני 460 ימים" על נתונים טריים
- **שורש:** שדה `price_updated_at` של הפריט משתנה רק כשהמחיר משתנה, אז מחיר יציב נראה ישן.
- **תיקון:** שדה `scraped_at` (מתי קובץ אישר את המחיר לאחרונה) ו-UI שנשען עליו.
- **לקח:** להבין מה שדה *באמת* אומר לפני שמציגים אותו למשתמש.

### סיפור 6: תמונה של מיונז על שימורי תירס
- **שורש:** התאמת תמונה לפי שם מוצר, רופפת מדי.
- **תיקון:** תמונה מוצגת רק אם הברקוד מתאים בקוד של המקור, או שהשמות מתאימים מילה במילה. בדיקת "known-good", dry run, לעולם לא דורסים תמונה קיימת, ברקודים קצרים (קודים פנימיים) אף פעם לא מותאמים.
- **המשך:** ב-Open Food Facts שלחתי 4 בקשות במקביל וקיבלתי **429**, אז ירדתי ל-2 עם הפסקה ארוכה יותר. מלמד כבוד ל-rate limit של אחרים.

### סיפור 7: האתר נהיה איטי בזמן העדכון
- **תסמין (נמדד ב-18:00):** ה-worker לקח 180% CPU ובקשות מחיר לקחו 3-15 שניות או נפלו.
- **תיקון:** ה-worker רץ עם `nice -n 15` (עדיפות נמוכה), שגיאת timeout של ה-DB מחזירה **503 עם Retry-After** במקום 500 עם stack trace, וכרטיסי התוצאות מנסים שוב אחרי 3 ואחרי 8 שניות.
- **לקח:** עבודת רקע ושירות משתמשים על אותו משאב דורשים תיעדוף מפורש.

### סיפור 8: rate limit שחסם את כולם (ו-sitemap שאמר http)
- **שורש:** אחרי שהוספתי Caddy מקדימה, כל הבקשות הגיעו ל-nginx מכתובת אחת (Caddy), אז ה-rate limit נספר "ללקוח אחד" לכולם.
- **תיקון:** `set_real_ip_from` לרשתות פרטיות בלבד + `X-Forwarded-For`, כדי שרק כותרת מ-proxy מהימן תתקבל.
- **לקח:** כשמוסיפים שכבת proxy, כל מה שמסתמך על "כתובת הלקוח" או "הפרוטוקול" נשבר.

### סיפור 9: באג כמות בעמוד המוצר
- הכפתור "+" הוסיף את כל הכמות מחדש בכל לחיצה (1, 2, 4...). תוקן: ברגע שהמוצר בסל, ה-stepper עורך את הכמות של הסל.

### סיפור 10: מבצעים: "כמעט נכון" הוא שגוי
- נמצאו בעיות במבצעים אמיתיים: מחיר ליחידה שנקרא בטעות כסך כולל, מבצע שהרשת מפרסמת בכמה מזהים (כפילויות), מבצעי "קופון"/ניסיון, קבצי Shufersal ו-Tiv Taam שנפסלו כולם בגלל פורמט מזהה מועדון (`<מספר> - <תווית>`).
- **הגישה:** כללים שמרניים. מבצע מוצג רק אם הוא זול ב-10-60% מהמחיר הזול ביותר שיש לנו, נתוני המבצעים של החנות צעירים משבוע, והמחיר מאושר בטקסט המבצע עצמו. מה שלא בטוח, מוצג כמידע בלבד ולא נכנס לחישוב הסל. מנוע המבצעים אומת מול מימוש איטי ופשוט על סלים אקראיים.

### סיפור 11: מוצר "סיטונאי" בתוך סופר
- ח. כהן (סיטונאי) הוסרה מהרשימה, ונבנה כלי להסרת רשת שלמה מה-DB: dry run כברירת מחדל, טרנזקציה אחת, ופועל תחת נעילת ה-ingest. בקוד review נמצא שרשימת מזהים ארוכה חורגת ממגבלת 32,767 placeholders של asyncpg, ולכן הרשימות נקשרות כמערך.

### סיפור 12: חנויות בלי כתובת
- Geocoding ב-Nominatim: חנויות בלי עיר השתמשו בשם כרמז, התאמות רחוק מהעיר נדחו, ושורה בעייתית נחשבת "לא נמצא" ולא "שורה מורעלת" שחוסמת את כל האצווה.

## 4. צוואר בקבוק ו-100x משתמשים

**מה הצוואר היום:** ה-DB על 2 ליבות, ושרת יחיד.

**מה כבר נעשה:** cache ב-nginx (GET, 5 דקות, כך ששאילתות זהות לא מגיעות ל-DB), materialized views, אינדקסים חלקיים, `statement_timeout=15s`, מודלים מבונים ידנית ב-`/basket/compare` (תשובה של 1.3MB; טעינת ישויות ORM מלאות לכל שורה הייתה רוב הזמן), ו-pool מוגבל.

**ב-100x משתמשים הייתי עושה, לפי סדר:**
1. CDN (Cloudflare) לקבצים סטטיים ול-GET של ה-API. רוב התנועה היא קריאה של נתונים שמשתנים פעמיים ביום.
2. Read replica ל-PostgreSQL; ה-API כבר משתמש בתפקיד קריאה בלבד, כך שהמעבר פשוט.
3. הרצה אופקית של ה-API מאחורי load balancer (הוא stateless), ו-pgbouncer (כבר יש תמיכה: `DB_PGBOUNCER=1`).
4. טבלת "הכי זול לכל מוצר" שמחושבת בסוף כל סבב, כדי לא לחשב בזמן בקשה.
5. Partitioning של `prices` לפי רשת אם הטבלה מגיעה לעשרות מיליוני שורות.
6. מדידה: `pg_stat_statements`, מדדי Prometheus, התראות.

**מה לא פתור במודע:** נקודת כשל יחידה, אין PITR (רק גיבוי יומי), `/basket/compare` מחזיר את כל החנויות אלא אם שולחים `limit`.

## 5. בדיקות, פריסה וניטור

**בדיקות:** pytest מול Postgres אמיתי (מסד זמני `sm_pytest` נוצר ונמחק), בדיקות ל-parsing, טעינה, מנוע מבצעים, API, מיגרציות (upgrade ← downgrade ← upgrade), worker, SEO. כ-290 פונקציות בדיקה, 347 הרצות בגלל פרמטריזציה (לפי ה-README). בדיקת "מוטציות" ידנית: הכנסתי 6 באגים מכוונים ובדקתי שהבדיקות תופסות. מנוע המבצעים נבדק מול מימוש ייחוס איטי על סלים אקראיים (differential testing).

**CI (GitHub Actions):** על כל PR ועל push ל-main: backend tests עם שירות Postgres, ו-frontend `tsc && vite build`.

**פריסה:** workflow נוסף שרץ **רק אחרי ש-CI עבר** על push ל-main, מתחבר ב-SSH עם מפתח ייעודי (`StrictHostKeyChecking=yes` מול known_hosts קבוע), ומריץ `deploy/deploy.sh <sha>`. `concurrency` מבטיח פריסה אחת בכל פעם. מיגרציות רצות לפני שה-API וה-worker עולים מחדש.

**ניטור:** `/health` (DB חי), `/health/data` (503 כשהנתונים ישנים מ-36 שעות או רשת לא נטענה 5 ימים), healthchecks.io ל-worker ולגיבוי, טבלת `ingest_runs`, לוגים מוגבלים (10MB × 3), גיבוי `pg_dump` יומי ל-7 ימים, סקריפט להעתקה מחוץ לשרת.

**איך הוכחתי שהטעינה בטוחה:** `kill -9` באמצע טעינה והפעלה מחדש ← נתונים סופיים זהים לטעינה נקייה. הסיבה: כל קובץ בטרנזקציה אחת יחד עם שורת ledger, ומחיקת הקובץ רק אחרי commit.

## 6. פרונט (React)

### Server Components מול Client Components, SSR/SSG/ISR
- **Client Component:** רץ בדפדפן, יכול להשתמש ב-state, effects ואירועים. **Server Component** (Next App Router): רץ רק בשרת, ניגש ל-DB ישירות, לא נשלח ל-bundle.
- **SSG:** נבנה בזמן build (בלוג). **SSR:** נבנה בכל בקשה (דף מותאם אישית עם SEO). **ISR:** SSG שמתחדש ברקע כל X שניות.
- **אצלי:** SPA טהור. SEO נפתר בשרת: ה-API מחזיר HTML עם תגיות head ו-JSON-LD לכל מוצר, ו-sitemap של כל מוצר עם מחיר. זה פחות אלגנטי מ-ISR אבל בלי שרת Node נוסף.

### ניהול state
- **מקומי:** `useState` בקומפוננטה. **גלובלי:** Context (אצלי `BasketContext`: כמה סלים, סל פעיל, undo, announcements לקוראי מסך, שמירה ב-`localStorage` עם fallback כשהוא חסום). **Server state:** נתונים מרוחקים עם מטמון, ביטול כפילויות, retry ו-revalidate. הכלי: **React Query / SWR**.
- **למה לא השתמשתי:** בלי מטמון משותף בין מסכים, ובכל מקום שהיה צריך כתבתי ידנית: ביטול בקשות ישנות (stale-response guards), ניסיון חוזר אחרי 3 ו-8 שניות, singleton לבקשת `/stats` (`statsRequest`). **תשובה כנה:** "היום הייתי משתמשת ב-React Query כדי לא לכתוב את זה ידנית."
- **סכנות של Context:** כל צרכן מתרנדר מחדש כשהערך משתנה. לכן `useMemo` על הערך ו-`useCallback` על הפעולות.

### re-renders, memoization, ביצועים
- קומפוננטה מתרנדרת כש-state/props/context שלה משתנים או שההורה מתרנדר. `React.memo` מונע רינדור כש-props לא השתנו (השוואה שטחית), `useMemo` שומר חישוב, `useCallback` שומר זהות פונקציה (חשוב כשהיא נשלחת ל-memo-child).
- **לא ממציאים:** מודדים קודם עם React DevTools Profiler. memoization בלי מדידה מוסיפה מורכבות בלי תועלת.
- **אצלי:** טעינה עצלה לפי מסלול (code splitting), תמונות WebP, גופן מקומי (Rubik) במקום Google Fonts, רשימות עם infinite scroll (IntersectionObserver), שלד טעינה (skeleton), וקריאות batch (40 ברקודים בבקשה אחת) במקום N בקשות.

### נגישות, טפסים, שגיאות
- **נגישות:** focus trap ו-`aria-modal` בחלונות, `aria-live` להודעות ("נוסף לסל"), ניגודיות צבעים, `prefers-reduced-motion`, אזור מגע 44px, hover רק במכשירים שתומכים בו, כפתורים עם שם נגיש.
- **טפסים/שדות:** 16px בטלפון כדי ש-iOS לא יעשה zoom בלחיצה על שדה.
- **שגיאות:** `ErrorBoundary` שתופס שגיאות רינדור, `ErrorState` משותף עם כפתור "נסי שוב", מצבי loading/empty/error בכל מסך.

## 7. בק-אנד

### Event loop, async/await, promises (Node, ובהשוואה ל-Python)
- Node: thread אחד שמריץ JS, ו-event loop שמטפל ב-callbacks אחרי שה-I/O (שרץ ב-libuv/OS) מסתיים. עבודת CPU כבדה **חוסמת הכול**. פתרון: worker threads או תהליך נפרד.
- `Promise`: ערך עתידי עם שלושה מצבים (pending/fulfilled/rejected). `async/await` הוא סוכר תחבירי מעליו. `Promise.all` מריץ במקביל, `Promise.allSettled` לא נכשל בשגיאה אחת. סדר: microtasks (promises) לפני macrotasks (`setTimeout`).
- **אצלי (asyncio):** אותו עיקרון. `await db.execute(...)` משחרר את ה-loop לבקשות אחרות. שני לקחים אמיתיים: (1) לא להריץ קוד CPU כבד בתוך endpoint (בניית תשובות גדולות, לכן בניתי מודלים ידנית וכתבתי JSON ישר), (2) ה-pool של החיבורים הוא המשאב המוגבל, ואם נגמר מחזירים 503.

### תכנון REST
- **סטטוסים:** 200 הצלחה, 201 יצירה, 204 בלי תוכן, 400 בקשה שגויה, 401 לא מזוהה, 403 אסור, 404 לא נמצא, 409 התנגשות, 422 ולידציה (FastAPI), 429 יותר מדי בקשות, 503 שירות לא זמין. **אצלי:** 400 לסל ריק, 404 למוצר שאין, 429 מ-nginx, 503 עם `Retry-After` כשה-DB עמוס.
- **Pagination:** offset/limit (פשוט, אצלי: `limit≤100`, `offset≤10000`) או cursor (יציב יותר כשהנתונים משתנים ואין "קפיצה" לעמוד). אצלי סדר יציב (`Product.id` כשובר שוויון) כדי שעמודים לא יחפפו.
- **Idempotency:** בקשה שאפשר לחזור עליה בלי תוצאה כפולה. GET/PUT/DELETE הם idempotent, POST לא. ליצירה מאובטחת משתמשים ב-`Idempotency-Key`. **אצלי:** ה-POSTים (`/basket/compare` ועוד) הם **קריאה בלבד**, כלומר בטוחים לחזרה; הטעינה ב-worker idempotent דרך ה-ledger והאינדקס הייחודי.
- **Versioning:** `/api/v1/` בנתיב. שינוי שובר ← v2, והישן נשאר זמן מה.

### אימות והרשאות (תיאוריה, כי אצלך אין משתמשים)
- **Session:** מזהה אקראי ב-cookie, המצב בשרת (Redis/DB). קל לבטל, דורש אחסון. **JWT:** טוקן חתום שהמצב בו; בלי אחסון בשרת, אבל קשה לבטל לפני תפוגה.
- **Access + refresh:** access קצר (דקות), refresh ארוך שמסתובב (rotation) ונשמר ב-cookie `HttpOnly; Secure; SameSite`.
- **איפה לשמור:** `HttpOnly` cookie מגן מ-XSS (JS לא קורא אותו) אבל חשוף ל-CSRF, ולכן `SameSite=Lax/Strict` וטוקן CSRF. ב-`localStorage` חשוף ל-XSS.
- **XSS:** הזרקת סקריפט. הגנה: escape (React עושה אוטומטית, חוץ מ-`dangerouslySetInnerHTML`), **CSP** (אצלי כותרת קפדנית ב-nginx: `script-src 'self'`). **CSRF:** אתר זדוני גורם לדפדפן לשלוח בקשה עם ה-cookie שלך.
- **מה כן יש אצלי:** תפקיד DB `api_ro` עם SELECT בלבד (ועדכון `image_url` בלבד), נבדק שנדחים UPDATE על שם, INSERT, DELETE, TRUNCATE, DROP. נתיבי `/tasks` שהיו פתוחים הוסרו. CORS רק ל-origin מוגדר.

### Validation, rate limiting, error handling
- **Validation:** Pydantic/`Query` בכניסה: אורך, טווחים (`lat 29-34`), סל עד 100 פריטים, כמות 1-99, גוף בקשה עד 1MB. בנוסף שמירה בצד נתונים: מחיר ≤ 0 נדחה, מחיר מתחת ל-0.10 לא נחשב.
- **Rate limiting:** nginx, `limit_req` 20 בק'/שנייה, burst 40, בנפרד 10/שנייה לתמונות (שיכולות לפנות לאתר חיצוני).
- **Error handling:** מטפל גלובלי ל-`DBAPIError` ול-timeout של pool שמחזיר 503 נקי; מצב "degraded" ב-`/health`; ב-worker כל רשת מבודדת בתהליך נפרד ולכן כשל אחד לא עוצר אחרים.

## 8. דאטה

### SQL מול NoSQL
- **SQL:** נתונים עם קשרים, עקביות (ACID), שאילתות מורכבות ו-JOIN. **NoSQL (מסמכים/key-value):** סכמה גמישה, scale אופקי קל, דפוסי גישה פשוטים וידועים מראש.
- **אצלי SQL:** רשת ← חנות ← מחיר ← מוצר, צריך להשוות מחירים בין חנויות, לצבור, ולמצוא "הזול ביותר" לפי תנאים מורכבים.

### סכמה של הפרויקט (לצייר על לוח)
- `chains` ← `stores` (ייחודי לפי `chain_id + store_id`, כי חנות "001" קיימת בכמה רשתות) ← `prices` (`store_id`, `product_id`, `price` Numeric(10,2), `is_current`) → `products` (`barcode` ייחודי)
- `promotions` (תלוי חנות; אינדקס ייחודי כולל מוצר)
- `ingested_files` (ledger), `ingest_runs` (היסטוריית סבבים)
- Views: `product_store_counts`, `product_price_range`, `promo_deals`

### החלטות סכמה שחשוב להסביר
- **`Numeric(10,2)` ו-`Decimal`, אף פעם `float`:** כסף חייב דיוק מדויק. `0.1 + 0.2 != 0.3` בנקודה צפה. קואורדינטות כן `Float`.
- **היסטוריית מחירים בלי בזבוז:** שורה אחת `is_current` לכל (חנות, מוצר), נאכף ע"י **אינדקס ייחודי חלקי** `WHERE is_current`. שינוי מחיר סוגר את הישן ומכניס חדש. אפשר גם לבנות גרף מחיר (יש `PriceSparkline`).
- **אינדקס חלקי כיסוי:** `ix_prices_current_product (product_id) INCLUDE (store_id, price) WHERE is_current` מאפשר Index-Only Scan ופחות גישות לטבלה.
- **`pg_trgm` + GIN:** חיפוש תת-מחרוזת ושגיאות כתיב בעברית ("גבימה" ← "גבינה"), עם `word_similarity` ו-threshold 0.3.
- **`fillfactor=90`** ו-autovacuum אגרסיבי על `prices` (טבלה עם הרבה עדכונים).
- **Materialized view** עם `REFRESH ... CONCURRENTLY` (דורש אינדקס ייחודי) כדי שקוראים לא ייחסמו.
- **נעילת advisory:** מונעת שתי הרצות worker חופפות.

### אינדקסים, JOIN, N+1, טרנזקציות
- **אינדקס:** מבנה (B-tree בדרך כלל) שמאפשר חיפוש בלי סריקה מלאה. מחיר: כתיבה איטית יותר ומקום. אינדקס עוזר רק אם השאילתה יכולה להשתמש בו (ראי סיפור 1).
- **N+1:** שאילתה אחת לרשימה ועוד שאילתה לכל פריט. פתרונות: JOIN, `IN (...)`, `selectinload`, או **endpoint batch** כמו שעשיתי (`price-summary-batch`: 40 ברקודים בבקשה אחת, 8.1ms ← 2.7ms).
- **טרנזקציה (ACID):** הכול או כלום. אצלי כל קובץ + שורת ledger באותה טרנזקציה, ולכן קריסה לא משאירה קובץ חצי-טעון או מסומן-טעון-בלי-נתונים.
- **רמות בידוד:** Read Committed (ברירת המחדל של Postgres) מגינה מ-dirty reads; Repeatable Read ו-Serializable מגינות מ-non-repeatable ו-phantom.
- **`EXPLAIN ANALYZE`:** כלי העבודה הראשון בכל בעיית ביצועים.
- **מיגרציות (Alembic):** 20 מיגרציות, כולן הפיכות. מיגרציה אחת סוגרת כפילויות `is_current` לפני בניית האינדקס הייחודי.

## 9. תכנון מערכת (קליל)

מסגרת תשובה לכל שאלה: **(1)** דרישות ומספרים, **(2)** API ומודל נתונים, **(3)** ארכיטקטורה בסיסית, **(4)** צווארי בקבוק ו-trade-offs.

### URL shortener
- דרישות: יצירת קישור קצר, הפניה מהירה, קריאות >> כתיבות (נניח 100:1).
- API: `POST /links {url}` ← `{code}`; `GET /:code` ← 301/302.
- נתונים: טבלה `links(code PK, url, created_at, owner_id?)`. הקוד: base62 של מונה, או 7 תווים אקראיים עם בדיקת התנגשות. מונה אטומי (sequence) מונע התנגשות אבל חושף סדר.
- ביצועים: cache (Redis) לקוד ← URL, כי הקריאות חוזרות. 301 מטמון בדפדפן אבל מפסיד ספירת קליקים, 302 לא.
- Scale: DB מחולק לפי hash של הקוד, ספירת קליקים אסינכרונית דרך queue.

### מערכת הערות
- משתמשים, מחברות, הערות; חיפוש טקסט (Postgres full-text); סנכרון בין מכשירים (last-write-wins או גרסאות); שיתוף = טבלת הרשאות. עריכה במקביל = optimistic locking עם `version`.

### פיד
- **Fan-out on read:** בעת פתיחה שולפים מהעוקבים וממזגים. פשוט, איטי למשתמש עם הרבה עוקבים. **Fan-out on write:** בעת פרסום דוחפים לפיד של כל עוקב (cache). מהיר לקריאה, יקר למי שיש לו מיליון עוקבים. בפועל הייבריד. pagination ב-cursor, לא offset.

### Caching, queues, scale (מושגים)
- Cache: איפה (דפדפן, CDN, nginx, אפליקציה, DB), מדיניות פינוי (LRU/TTL), invalidation (הבעיה הקשה). **אצלי:** nginx cache ל-GET של 5 דקות כי הנתונים משתנים פעמיים ביום.
- Queue: עבודה אסינכרונית, ניתוק בין מייצר לצרכן, retry. **אצלי:** ה-worker מתזמן סבבים; אם היה צריך עבודה לפי דרישה הייתי מוסיפה Redis/RabbitMQ.
- Trade-offs: עקביות מול זמינות (CAP), cache מול טריות, פשטות מול scale.

## 11. AI

**שאלה: איך את משתמשת ב-AI בעבודה ואיך את מוודאת שהקוד נכון?**

**שילוב LLM ב-API (מושגים):** prompt ברור עם דוגמאות, פלט מובנה (JSON schema) ולידציה שלו, **עלות** (טוקנים בקלט ובפלט, caching של prompt, מודל קטן למשימות פשוטות), **כשלים** (hallucination, timeout, rate limit ← retry עם backoff, fallback), **אבטחה** (prompt injection: לא סומכים על טקסט שמגיע מהמשתמש או מדף חיצוני), לוג והערכה (eval set).
**רעיון אמיתי לסלי:** נרמול שמות מוצרים (למשל "חלב תנובה 3% 1 ליטר" ← שם אחיד) והתאמת מוצרים בין רשתות בלי ברקוד.

```js

const unique = arr => [...new Set(arr)];

// 2. ספירת תדירות מילים
const freq = s => s.toLowerCase().split(/\s+/).filter(Boolean)
  .reduce((m, w) => (m[w] = (m[w] || 0) + 1, m), {});

const groupBy = (arr, key) => arr.reduce((m, x) => ((m[x[key]] ??= []).push(x), m), {});

// 4. שני מספרים שסכומם target, O(n)
function twoSum(nums, target) {
  const seen = new Map();
  for (let i = 0; i < nums.length; i++) {
    const j = seen.get(target - nums[i]);
    if (j !== undefined) return [j, i];
    seen.set(nums[i], i);
  }
  return null;
}

// 5. פלינדרום
const isPal = s => { const t = s.toLowerCase().replace(/[^a-z0-9א-ת]/g, ''); return t === [...t].reverse().join(''); };

// 6. debounce (שימושי לשדה חיפוש, כמו שיש לך)
function debounce(fn, ms) { let t; return (...a) => { clearTimeout(t); t = setTimeout(() => fn(...a), ms); }; }

// 7. הסל הזול ביותר: סכום לפי חנות, מיון מהזול ליקר
function cheapestStore(prices /* [{store, barcode, price}] */, basket /* {barcode: qty} */) {
  const totals = {};
  for (const p of prices) if (basket[p.barcode]) totals[p.store] = (totals[p.store] || 0) + p.price * basket[p.barcode];
  return Object.entries(totals).sort((a, b) => a[1] - b[1]);
}
```
