# HLD: סופרמרקט פרייסס על VPS יחיד בישראל

**סטטוס:** גרסה 2 (אחרי סקירה חיצונית וממומשת בענף `cloud-vps-ingestion`) · **תאריך:** 2026-10-08

> גרסה 1 הציעה Supabase + Vercel serverless. הסקירה החיצונית מצאה שהיא לא מתאימה
> (מכסת 500 MB, זמן תגובה בין שרת ל-DB, pooler, scraping ב-serverless). הוחלט על
> **שרת VPS אחד בישראל** שמריץ הכול. המסמך הזה מתאר את מה שנבנה בפועל.

## 1. בעיה ומטרות

המערכת משווה מחירי סופרמרקטים בישראל. כל הרכיבים רצו על מחשב אחד: 75 GB של קבצי XML,
DB מקומי עם רשת אחת (שופרסל), וסקרייפר ידני.

| מטרה | איך מתמלאת |
|---|---|
| אפס נתונים על המחשב | הכול על VPS; קבצי ה-XML נמחקים אחרי הטעינה |
| עדכון אוטומטי | worker שרץ פעם ביום ב-06:00 (שעון ישראל), עם עד 2 ניסיונות חוזרים אם הסבב נכשל |
| כל הרשתות, כולל 12 הישראליות-בלבד | שרת עם IP ישראלי (נבדק מ-IP ביתי, ראו §9) |
| עלות נמוכה | שרת אחד (~4 GB), בלי שירותים מנוהלים |
| כללי הפרויקט נשמרים | `Decimal`, DB אסינכרוני, `(chain_id, store_id)`, `is_current`, שם מוצר first-seen, מיון מהזול ליקר |

**אי-מטרות:** חשבונות משתמש, real-time, HA (ראו §10).

## 2. ארכיטקטורה

```
 פורטלי הרשתות ──► worker ──► PostgreSQL ◄── API (תפקיד api_ro, קריאה בלבד) ◄── nginx ◄── משתמשים
 (FTP / אתרים)    scrape→parse→delete   │         workers=2                 cache+rate limit
                                        └──► backup (pg_dump יומי)
```

כל הרכיבים ב-`docker-compose.yml`. רק nginx חשוף החוצה (פורט 80); ה-DB לא.

| שירות | תפקיד |
|---|---|
| `db` | PostgreSQL 16, מכוון לשרת 4 GB, אינדקסים חלקיים, fillfactor 90 |
| `migrate` | רץ פעם אחת בכל עלייה (`alembic upgrade head`) כבעל הסכימה |
| `api` | FastAPI, מתחבר כ-`api_ro` (קריאה בלבד + עדכון `products.image_url` בלבד), `read_only` filesystem |
| `worker` | `python -m app.worker`: לולאת הטעינה |
| `backup` | `pg_dump` יומי, שומר 7 ימים |
| `frontend` | build של Vite ב-nginx סטטי |
| `nginx` | proxy: cache של GET ל-5 דקות, 20 בקשות לשנייה ללקוח, כותרות אבטחה, gzip |

## 3. צינור הטעינה

```
לכל רשת (במקביל, מבודדת):
  scrape (subprocess, timeout, 2 ניסיונות; רק קבצי חנויות ו-Full) ──► קבצי XML
  parse: לכל קובץ, מהישן לחדש, חנויות לפני מחירים:
     1. בדיקה שה-XML שלם (assert_well_formed)
     2. טרנזקציה אחת: טעינה מרוכזת + שורת ledger
     3. commit ◄── ורק אז מחיקת הקובץ
```

### עקרונות

- **ledger (`ingested_files`):** קובץ נחשב טעון כשיש לו שורה `done`, לא לפי מה שיש בדיסק.
- **דה-דופליקציה של ההורדות:** מתבצעת ע"י מסד הסטטוס של הספרייה (`dumps/status/<chain>.json`, לפי שם קובץ), לא לפי קיום קובץ בדיסק. לכן מחיקת קבצים בטוחה (הוכח, §8). הקבצים האלה נגזמים בכל סבב (events 3 ימים, הורדות 14 יום), כי הספרייה קוראת את כל ה-JSON בכל בדיקת קובץ.
- **טעינה מרוכזת בקבוצות של 500:** מוצרים `ON CONFLICT DO NOTHING` (השם הראשון נשאר), השוואת מחירים ב-Python, ולכל קבוצה לכל היותר UPDATE אחד (סגירה), INSERT אחד, UPDATE אחד (touch).
- **מחירים:** `Decimal` מעוגל ל-2 ספרות לפני השוואה, כך ש-`12.345` לא נראה כשינוי מול `12.35`.
- **מחיר ישן לא דורס חדש:** שורה עם `price_updated_at` ישן מזה שב-DB מתעלמים ממנה.
- **שורה נוכחית אחת:** אינדקס ייחודי חלקי `(store_id, product_id) WHERE is_current`. סוגרים לפני שמכניסים.
- **מחיר שלא השתנה:** לא נכתב. `scraped_at` מתעדכן לכל היותר פעם ב-24 שעות.
- **קובץ Full סוגר מוצרים שנעלמו,** אבל רק אם הוא מפרט לפחות 50% ממה שיש לנו בחנות (הגנה מקובץ חתוך).
- **קובץ Full אחד לכל חנות:** מכל חנות טוענים רק את ה-Full הכי חדש בסבב. השאר מסומנים `superseded` ולא נטענים, וגם קובץ ישן שמופיע אחרי שחדש ממנו כבר נטען לא מחזיר את החנות אחורה. קבצי דלתא לא מורדים (Full יומי מתקן את עצמו, ודלתא עלולה לפספס שינויים).
- **קבצים פגומים:** XML לא שלם או "0 שורות מקובץ אמיתי" נכשלים. הקובץ נמחק ומסומן לשליפה מחדש. אחרי 3 כשלונות הוא עובר ל-`dumps/_quarantine/` ולא נשלף שוב.

### בידוד כשלים

| כשל | מה קורה |
|---|---|
| אתר רשת השתנה / הסקרייפר זרק שגיאה | נרשם ב-`ingest_runs`, שאר הרשתות ממשיכות; הפרסור של מה שכבר בדיסק ממשיך |
| הסקרייפר נתקע | נהרג אחרי `SCRAPE_TIMEOUT_SECONDS` (כל קבוצת התהליכים) |
| הורדה חתוכה | נדחית לפני כל כתיבה (הספרייה "מתקנת" XML חתוך בשקט ומחזירה רק את מה שלפני החיתוך) |
| ערכים מקולקלים בשורה (NaN, שלילי, גדול מדי, NUL, ברקוד ארוך) | השורה מדולגת ונספרת, שאר הקובץ נטען |
| קובץ ישן / כפול / לא לפי סדר | מתעלמים לפי תאריך; האינדקס הייחודי מגן |
| קריסה / `docker stop` / `kill -9` | כל קובץ טרנזקציה; הנעילה משתחררת לבד; שורות "running" תקועות נסגרות בעלייה הבאה |
| שתי הרצות במקביל | נעילת advisory ב-Postgres (קוד יציאה 2) |
| דיסק מלא | הורדות נעצרות מתחת ל-`MIN_FREE_DISK_GB`; הטעינה ממשיכה ומפנה מקום |
| ה-DB נפל | ה-API מחזיר 503 ב-`/health`; ה-worker מנסה שוב בסבב הבא |

## 4. מודל נתונים

קיים: `chains`, `stores`, `products`, `prices`, `promotions`. נוסף במיגרציה `b7d41c9e5a20` (הפיכה):

- `ingested_files`: ledger לפי `(source_folder, file_name)`, סטטוס, ניסיונות, שגיאה אחרונה.
- `ingest_runs`: שורה לכל סבב, ולכל רשת ושלב בתוכו.
- אינדקסים על `prices`: **הוסרו** `ix_prices_product_store`, `ix_prices_is_current`, `ix_prices_scraped_at`, `ix_products_barcode` (כפול ל-`products_barcode_key`). **נוספו** `uq_prices_current_store_product` ו-`ix_prices_current_product (product_id) INCLUDE (store_id, price) WHERE is_current`.
- `fillfactor=90` ו-autovacuum אגרסיבי על `prices`.
- המיגרציה סוגרת כפילויות `is_current` קיימות (הכי חדש נשאר) לפני בניית האינדקס, ומעניקה הרשאות ל-`api_ro` אם הוא קיים.

## 5. ה-API

החוזים לא השתנו. מה שהשתנה סביבו:

- נתיבי `/api/v1/tasks/*` **הוסרו** (היו פתוחים לכולם), וגם Celery ו-Redis.
- CORS: רק `FRONTEND_URL` (או כתובות פיתוח), לא `*`.
- `/health`: בודק DB, 503 אם לא עונה. `/health/data`: 503 כשהסבב המוצלח האחרון ישן מ-`MAX_DATA_AGE_HOURS`.
- חיבור: `pool_pre_ping`, גודל pool מוגדר, תמיכה ב-pgbouncer (`DB_PGBOUNCER=1`) אם יידרש.
- `statement_timeout=15s` לתפקיד ה-API.

## 6. אבטחה

תפקיד `api_ro`: SELECT על הכול, UPDATE על `products.image_url` בלבד. נבדק: UPDATE של `name`, INSERT למחירים, DELETE, TRUNCATE, DROP, CREATE נדחים. הסיסמאות חובה ב-`.env` (בלי ברירות מחדל). ה-DB לא חשוף. ה-API רץ עם filesystem לקריאה בלבד ובלי הרשאות מורחבות.

## 7. תפעול

מדריך מלא ב-`docs/deployment.md`: הקמה, preflight לשרת חדש, ניטור (`/health`, `/health/data`, healthchecks.io), גיבוי ושחזור, עדכון, ושדרוג הספרייה.

## 9. IP ישראלי

מהמחשב הנוכחי (כתובת ביתית, בזק, נתניה) הורדתי קובץ חנויות אמיתי מ-**12 מ-12** הרשתות הישראליות-בלבד
שקיימות בגרסת הספרייה המותקנת. קופיקס (COFIX) לא קיימת בגרסה 1.0.8.

**לא נבדק:** כתובת של מרכז נתונים. אתרי רשתות לפעמים מתייחסים אחרת ל-IP של ענן. לכן חובה להריץ
`python -m app.scraper.preflight` על השרת החדש לפני שסומכים עליו.

## 10. מה לא נפתר (במודע)

- **נקודת כשל יחידה:** שרת אחד. שחזור = גיבוי + הרצה מחדש של ה-worker.
- **גיבוי מחוץ לשרת:** הדמון כותב לדיסק המקומי. העתקה החוצה (rclone/S3) דורשת חשבון והחלטה שלך.
- **שחזור נקודתי בזמן (PITR):** אין WAL archiving; גיבוי יומי בלבד.
- **ניטור:** `/health/data` ו-healthchecks.io דורשים שתפתחי חשבון והגדרת התראות.
- **TLS:** HTTP בלבד; לשים Cloudflare או Caddy מקדימה.
- **מבצעים (Promo):** לא נטענים. קבצי Promo לא מורדים כרגע (`SCRAPE_PROMOS=false`), כדי שלא יצטברו בדיסק.
- **שאר 29 הרשתות** לא נטענו ל-DB בבדיקות; יטענו בסבב הראשון על השרת.
- **הערכת גודל מלאה:** עדיין אקסטרפולציה מרשת אחת (שופרסל = 1.54M שורות); לא נמדדה על כל הרשתות.
- **parse על ליבה אחת:** ה-XML נקרא בתהליך אחד, ולכן ריבוי רשתות במקביל לא מנצל כמה ליבות. לא צוואר בקבוק בסבב היומי.

## 11. רעיונות הבאים (לפי תועלת)

1. גיבוי החוצה + בדיקת שחזור חודשית.
2. טעינת Promo (טבלה ומודל קיימים; צריך טוען).
3. טבלת "הכי זול לכל מוצר" שמתעדכנת בסוף כל סבב, לדף הבית.
4. WAL archiving (WAL-G / pgBackRest) לשחזור לנקודת זמן.
5. פיצול `prices` ל-partitions לפי רשת, אם הטבלה תעבור עשרות מיליוני שורות.
6. מדדים (pg_stat_statements, Prometheus) והתראות על כשלי רשת בודדת.
